# 003. Инкрементальная агрегация по потомкам

- Status: Accepted
- Date: 2026-09-15
- Tags: domain, performance, realtime

## Контекст

ТЗ:

- суммарные показатели = узел + все потомки;
- средняя эффективность взвешена по headcount;
- агрегация считается один раз после загрузки и мемоизируется;
- после live-патча пересчёт **только** затронутого узла и его предков.

На фикстуре ≥40 узлов полный пересчёт дешевле 1 мс, но инвариант "соседняя ветка не тронута" должен быть закрыт в любом случае.

## Решение

Два входных пункта, два разных алгоритма.

1. **Snapshot с сервера** (`GET` / recovery): `aggregateTree(index)` — полный постпорядок, O(n). Результат — `Map<id, Aggregate>` в store.
2. **Патч:** `applyPatch` обновляет узел и поднимается по `parentId`, O(depth).

`Aggregate` хранит `weightedSum` вместе с `totalHeadcount` / `totalBudget` / `weightedPerformance`, чтобы родитель пересчитывался из детей без спуска в листья:

Дети пропатченного узла не меняются.

Тест-оракул: полный `aggregateTree` после патча равен инкрементальному Map.

## Последствия

Положительные:

- ТЗ выполняется буквально.
- Fade 1.5 с можно вешать на `touchedIds`, не на весь грид.
- Unit-тест домена без React закрывает главный риск (неверное среднее).

Отрицательные:

- `applyPatch` сложнее полного пересчёта.
- Смена `parentId` (переезд команды) этим алгоритмом **не** покрыта — контракт v1 такие патчи не шлёт. Если появятся, нужен полный `buildTree` + `aggregateTree`.

Нули: если `totalHeadcount === 0`, `weightedPerformance = 0`, не `NaN`. Патч, обнуляющий headcount, обязан обновлять предков тем же правилом.
