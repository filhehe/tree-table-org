# 004. NL-поиск: клиентский парсер, не LLM API

- Status: Accepted
- Date: 2026-09-15
- Tags: search, ai-feature, offline
- Relates: [data-model.md](../data-model.md), [architecture.md](../architecture.md)

## Контекст

Строка поиска принимает естественный язык, ответ — структурированный фильтр на клиенте, fallback текстовый поиск.

Ограничения:

- `docker compose up` без секретов и без счёта за токены;
- нет авторизации, нет внешнего API;
- JS gzip ≤ 200 КБ — не тащим SDK модели;

NL → structured output — отдельный слой с контрактом, а не `string.includes` под видом AI.

## Решение

Два каскада в одном input (после debounce 250 мс, общий с текстовым фильтром):

```
rawQuery → parseNl(rawQuery) → StructuredFilter | null
         → если null или parser-confidence низкая
           → fallback { nameContains: rawQuery }
```

`StructuredFilter` — в [data-model.md](../data-model.md). Применение фильтра — чистая функция.

Дерево может либо фильтровать видимость, либо только подсвечивать совпадения, делаю выбор в пользу подсвечивания, в рамках ТЗ этого будет достаточно.

Уточнение UX:

- Таблица: строки, не прошедшие фильтр, скрыты.
- Дерево: несовпавшие узлы приглушены, совпавшие — full opacity.

Парсер: детерминированные правила (regex + словари), без сети.

Примеры фраз → фильтр:

| Запрос                        | StructuredFilter                         |
| ----------------------------- | ---------------------------------------- |
| `эффективность выше 80`       | `{ minPerformance: 80 }`                 |
| `бюджет больше 1 млн`         | `{ minBudget: 1_000_000 }`               |
| `команды` / `уровень команда` | `{ level: 2 }`                           |
| `отдел платежей`              | `{ level: 1, nameContains: "платежей" }` |
| `больше 20 сотрудников`       | `{ minHeadcount: 20 }`                   |
| `alpha` (нет шаблона)         | `{ nameContains: "alpha" }`              |

Словарь операторов: `выше/больше/>`, `ниже/меньше/<`, `от`, `до`, `уровень`, `дивизион|отдел|команда`. Числа: `80`, `1 000`, `1млн`, `1.5м`.

Контракт функции:

```ts
function parseNl(query: string): {
  filter: StructuredFilter;
  mode: "structured" | "text";
};
```

`mode` нужен UI: бейдж «фильтр» vs обычный поиск — чтобы было видно, что NL сработал.

В проде тот же `StructuredFilter` может заполнять LLM (`response_format: json_schema`).
Клиентский код применения фильтра **не меняется**. Это и есть точка расширения.

## Альтернативы

| Вариант                       | Почему нет                                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------------------- |
| Вызов Claude/OpenAI с сервера | Ключ в `.env`, сдача без ключа ломается; docker «не одной командой»; задержка и деньги на проверке. |
| Локальная модель в контейнере | Размер образа, время старта, не про frontend-тест.                                                  |
| Только substring              | Не выполняет «структурированный фильтр», не заделка под расширение до LLM.                          |

## Последствия

Положительные:

- Offline, детерминированные тесты парсера.
- Один тип фильтра для будущего LLM.
- Бюджет бандла не страдает.

Отрицательные:

- Покрыты только заложенные шаблоны
- Русские падежи частично: лучше нормализовать (`команда/команды/команд` → level 2).

Объём словаря держать маленьким: 10–15 правил, unit-тесты на таблицу примеров выше.
